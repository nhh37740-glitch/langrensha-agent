## 分层速览（对应主图中的方框）

| 层 | 源码 | 职责 |
| --- | --- | --- |
| 页面与场景 | `前端/src/main.js`、`前端/src/scene.js` | 同源 API 请求；把受限状态交给 DOM 与 Phaser，不自行裁定 |
| HTTP 入口与认证 | `src/langrensha/web.py` | 同源头/口令/摘要校验、会话表、逐窗口推进 |
| 应用服务与受限会话 | `src/langrensha/service.py` | `GameService` 事务编排；`PlayerSession` 固定已认证操作者 |
| 领域规则 | `src/langrensha/full_game.py`、`src/langrensha/rules.py` | 纯状态机裁定；身份、席位、事件等基础（无数据库 I/O） |
| 可见性过滤与呈现 | `src/langrensha/full_game.py`、`src/langrensha/presentation.py` | `player_view` 先按受众/死亡/身份过滤；`present` 转网页数据 |
| 只读检索 | `src/langrensha/retrieval.py` | 只在已过滤视图与世界书内检索，来源有编号 |
| AI 编排与札记 | `src/langrensha/ai.py`、`src/langrensha/assistant.py` | LangGraph 有界决策；札记模型只整理已检索来源 |
| 持久化 | `src/langrensha/store.py` + SQLite 文件 | 事务快照、幂等回执、拒绝与决策审计、会话摘要 |

## 示例讲什么

默认主图使用**合成数据**：4 号镇民在白天投票给 7 号。页面提交 `request_id`、`phase_id`、`expected_version`、`tool`、`payload`；HTTP 层用 cookie 摘要查出固定 game/seat；`PlayerSession` 把操作者固定为 4 号；`GameService._submit` 在 `Store.transaction()` 里加载快照、调用纯函数 `full_game.reduce_action` 裁定、保存新快照；成功时 version+1 并记录回执，最后 `player_view` 先按受众/死亡/身份过滤，再交给 `presentation.present` 转成页面数据。

`reduce_action` 会拒绝：字段不合法、请求回执冲突、阶段过期（stale_phase）、版本过期（stale_version）、工具不在当前允许列表（tool_not_allowed）、目标不可选（invalid_target）。拒绝只写 `rejections` 审计，**不保存快照、不增加版本**。模型说“我投票了”不会生效，只有原生工具调用经过同一入口才算行动。

## 课堂概念 → 本项目怎么用 → 为什么需要

| 课堂概念 | 本项目中的实现 | 为什么需要 |
| --- | --- | --- |
| 分层与模块化 | 页面、HTTP、应用服务、规则、呈现、检索、持久化各管一件事；`pyproject.toml` 的 Import Linter 契约把依赖方向变成可执行检查 | 改页面不必改规则；规则可以脱离网络和数据库单测 |
| 封装与最小权限 | `GameService`/`Store` 不暴露给页面或模型；模型只拿到 `PlayerSession`，查询走 `query`、行动走 `submit` | 防止一次提示词注入就改写对局或读越权资料 |
| 认证 vs 授权 | 认证在 `web.py:62-77`（cookie 摘要 → 固定 game/seat）；授权在 `full_game.player_view`（按事件受众、死亡时间、身份过滤）与工具目标校验 | 知道“你是谁”不等于知道“你能看什么/做什么” |
| 有限状态机 | 当前阶段 + 合法工具决定下一状态；`reduce_action` 校验阶段、版本、工具、目标与幂等回执后，才复制状态并施加行动 | 非法状态转换必须被拒绝，不能靠模型自觉 |
| 数据库事务 | `Store.transaction()` 使用 `BEGIN IMMEDIATE`，加载→裁定→保存同事务提交，异常回滚 | 避免“行动生效一半”：例如事件写了但版本没加 |
| 并发控制与幂等 | `expected_version` 不符 → `stale_version`（乐观并发）；`request_id` + `receipts` 重放同一结果（幂等，内容不同则 `request_id_conflict`） | 这两个概念解决不同问题：一个防覆盖别人的新状态，一个防网络重试重复生效 |
| 有界控制流 | `DecisionRunner` 用 LangGraph 的 model→dispatch 循环，轮数上限 `AI_MAX_ROUNDS`（默认 3）；耗尽或模型故障走受控弃权并写决策报告；查询工具只读，行动仍进 `reduce_action` | 让 AI 有自主性但不会无限循环或越过规则 |

## AI 查询与行动的分流

- 触发：`web.py:175-197` 的 `/api/advance` 只在“待行者不是当前真人且对局未结束”时，为 AI 绑定独立 `PlayerSession` 并运行 `DecisionRunner`；不跳过真人、不替真人弃权。
- 查询：`ai.py:203-231` 中 `QUERY_TOOLS` 走 `session.query` → `retrieval.query`，只读、来源有编号。
- 行动：其余工具走 `session.submit`，和真人一样进入 `reduce_action`，仍校验阶段/版本/权限/目标。
- 边界：`pyproject.toml` 的 Import Linter 规则禁止 `ai`/`assistant` 直接依赖 `service`/`store`/`web`；模型不接收主持快照，也不能直接写 SQLite。决策报告由服务层 `_record_decision` 落盘。
- 札记（真人辅助）：`web.py:79-88` 先检索，再可选调用 `assistant.assist`；模型只得到可见来源和 `compose_note` 工具，不能执行对局行动，答案不会自动发表。
