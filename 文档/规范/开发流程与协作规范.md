# 软件开发流程与协作规范

制定日期：2026-10-23（北京时间）。适用项目：本仓库；本地原目录为 `X:\狼人杀agent`。

本文件规定怎么开展工作，不确定产品需求、技术选型或模块方案。当前阶段统一记录在 [项目说明](../../项目说明.md)，各阶段按用户实际指示推进。

## 1. 基本原则

- 按“规范 → 需求分析 → 架构与设计模式 → 详细设计 → 编码与测试 → 验收交付”的顺序推进。发现前提有误时返回对应阶段修订。
- 用户决定产品目标、范围和优先级。助手可以整理、提问和提出建议，不能将自己的补充写成用户已确认的需求。
- 每轮先识别用户要求的是讨论、记录、制定规范、需求分析、设计还是实施，只完成当前已授权范围。
- 不因用户举例就指定首版内容，不因用户询问某技术就自行采用，不因讨论过功能就开始划分模块或编写代码。
- 用户已明确表达的选择保留原始依据；进入相应阶段时结合完整条件核对，不擅自扩大或抹去已有决定。

## 3. 各阶段的边界

- 规范阶段：只规定工作方法，不代写需求清单、技术方案或模块设计。
- 需求阶段：回答“谁在什么场景需要什么结果、有什么限制、如何验收”；技术偏好原样登记，不据此展开接口和实现。
- 架构阶段：方案须说明对应哪项需求及取舍依据；未经比较，不以“先进”“成熟”等形容词代替判断。
- 详细设计阶段：明确目标文件或模块、影响范围与验收方式后再准备实施；遵守用户已确定的业务归属约束。
- 实施阶段：不把需求缺口当成自由扩展的授权，遇到影响范围的变更先返回相应阶段处理。
- 验收阶段：区分已修改、已验证、已构建、已部署和线上已验收，只报告有证据的状态。

涉及项目具体业务的只读调研也必须先建立或关联真实开放的 Issue，读取正文与有效讨论，明确范围及验收条件后再交给 DSH 执行；已有对应 Issue 时复用。小说、世界书等业务调研按一 Issue、一独立分支、一 PR，经审查与既有 CI 交付，不能因“只读”“临时任务”或使用 goal、子 Agent 而绕过。用户提供资料、要求继续或无人值守，不表示豁免 Issue 流程。调研结果属于证据或候选方案，不自动成为产品决定。此条按 2026-10-25 用户纠正更新。

监督者负责测试、验收、提单、GitHub 规则维护与推进；业务调研、设计与开发由 DSH 按 Issue 执行。新增依赖、修改业务源码、迁移目录、发布或部署均不能由流程规范本身产生授权。

## 6. GitHub 开发与合并流程

用户于 2026-10-23 明确：特性和 Bug 都通过 GitHub Issue 管理并合入主线，使用 GitHub 构建。这里的具体做法是 **Issue 记录工作、PR 合并交付、GitHub Actions 自动构建与检查**。2026-10-25 用户进一步明确：本流程同样覆盖涉及项目具体业务的调研、设计和正式文档交付，不能等到编码才关联 Issue。

1. **立项**：开展或派发业务任务前，先建立或关联真实开放的 Issue，读取正文与有效讨论；每项新特性、Bug、业务调研、设计及正式文档交付均适用，已有对应 Issue 时复用。写清目标、范围和验收结果；Bug 还须记录发生位置、复现步骤、期望与实际结果、证据。标明受影响的业务模块；必要时按本项目规则列出该模块下修改或新增的一级模块及用户可得到的结果。讨论和设计文档仍按阶段流程审定，Issue 不代替需求与设计依据。
   - Agent 创建或编辑 Issue 时，问题描述正文不超过 300 个汉字；提交前自行核对，超过先精简再提交。标题与评论不属问题正文，本规则与第 8 节 PR 评论的 300 汉字规则分开执行。
2. **开发**：从对应 Issue 建工作分支，在分支内实施并本地验证。不要直接修改或推送主线。一个 PR 聚焦可审阅的改动，并链接对应 Issue；如果同一修复影响多个 Issue，在 PR 中逐一说明。
3. **提审**：PR 目标为主线 `main`，写明改动、验收办法和测试结果。使用 `Closes #编号` 关联可在合并时关闭的 Issue；尚未解决的事项只引用，不误关。前端交互和动画的 PR 附截图或短视频，并说明操作反馈。
4. **GitHub 构建**：GitHub Actions 对每个 PR 和主线变更运行。Python 后端执行依赖安装、静态检查、必要测试与可分发包构建；HTML/CSS/JavaScript 前端执行依赖安装、静态检查、前端构建及关键交互验证。Python 不以“编译成功”代替运行和测试通过；具体命令在代码及构建方案确定后落地。
5. **合并与标记**：保护 `main`，要求经 PR 合并且必需的 Actions 检查通过；审阅确认符合 Issue 验收内容后合并。每个新功能合入后，在该功能对应的主线提交上创建唯一 Git tag，能追溯到 Issue、PR 和构建结果；Bug 仍走 Issue/PR 流程，不因此自动视作新功能。合并后核对 Issue 关闭状态和主线构建结果。构建通过只代表构建与检查完成；最终还须部署到用户服务器，核对部署版本、实际入口和线上对局结果，分别记录部署及线上验收证据。

仓库初始化时配置中文 Issue/PR 模板、基础 Actions 与主线保护规则；待业务代码出现后补全 Python 与前端构建命令，并用一次特性和一次 Bug 的真实改动验证全流程。业务代码经 Issue、分支、PR 与 GitHub Actions 合入；Codex Cloud 与本地 DSH 均可实施，以当轮用户授权和 Issue 范围为准。

依据：[GitHub 关联 PR 与 Issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)、[保护主线](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[Python 构建与测试](https://docs.github.com/en/actions/tutorials/build-and-test-code/python)、[Node.js 构建与测试](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)。

## 8. 沟通方式

默认简体中文，先给结论，普通反馈尽量控制在 200 字内。详细内容放文件；只汇报本轮实际完成的工作，不用大段计划代替结果，不在用户补充想法时抢先推进后续阶段。

Agent 在 GitHub PR 对话中的单条评论不超过 300 个汉字（2026-10-24 用户明确要求）；超过时发送前自动拆分为多条或拦截，不发送超限评论。只统计正文汉字，标点、链接地址与代码片段（围栏代码与行内代码）不占额度；发送前可用 `.github/scripts/校验PR评论长度.py` 检查或拆分。该限制不改变 Issue、代码内容或用户评论的既有规则。

## 9. DSH 单人串行执行（2026-10-26 用户高优先级要求）

**DSH 只由单个会话串行处理 Issue；2026-10-25 的 leader + 原生 subagent 团队并行授权已由本轮指令取代。**

- 禁止创建、fork 或恢复子代理、团队及其他并行开发会话；原生 `tool-subagent`、`tool-subagent-fork` 委派入口在持久配置中禁用，不以队员数量上限代替入口禁用。
- 同一时刻只处理一个 Issue，完成当前 Issue 后才领取下一个。每个 Issue 一个独立 worktree、分支和 PR，PR 只交付自己的 Issue。
- 每个 Issue 的调研、设计、实现、测试、审查与合并在同一会话内串行完成；等待 CI/审查时仍处理当前 Issue，不另开代理或开发会话。
- 任一 PR 因主线新合入而过期时，同步最新 `main`、解决冲突并重新验证对应新 head；不得用旧 head 结果代替。
- 旧串行监督脚本与已停用的 GitHub Actions 调度作为历史机制记录，不重新启用；不另搭团队平台或新门禁。

根 `AGENTS.md`、项目开发 Agent 与 Copilot 指引同步本规则；适用于后续所有项目任务。

## 10. PR 的 Issue 关联、验收节奏与 Codex 核查（2026-10-25）

用户要求 DSH 提 PR 时必须提供对应 Issue。监督者验收按大版本（项目版本/里程碑，人工判定）组织，不要求每个 PR 都执行一次；GitHub Codex code review 默认执行，仅当官方明确 token 或审查配额不足时可跳过。跳过时须在 PR 正文或评论记录跳过原因、影响范围、实际补充检查及证据；配额例外不放行已发现的问题，审查或补充检查发现的问题仍须修复并重新核查，不得把 running、超时或未经确认的额度问题当作跳过依据。PR 正文用唯一 `Issue: #编号` 声明当前任务，附本次范围、正式需求/设计路径和逐项验收证据；由 DSH 自动创建的 PR，其分支、Issue 与该 PR 对应的活动任务须一致。DSH 单人串行时同一时刻只处理一个活动 Issue，且每个 PR 只对应自己的 Issue。Codex 按根 `AGENTS.md` 的 Code review guidelines 读取真实 Issue 与正式依据，核查 diff 是否遗漏、越界或夹带其他问题。缺少关联或已发现问题未修复时不得验收；发送 review 请求本身不算通过。仓库不另设 Issue 关联 CI；执行前的一致性检查仍保留，避免错误任务先行实施。

- GitHub 合并 API 的 `--author-email` 受当前认证账户已验证邮箱限制，官方 noreply 可能返回 `Invalid email address`。此时可省略该参数，让 GitHub 使用已验证仓库所有者身份，仍显式传递干净的 `--body-file`。不更改账户邮箱设置，不输出常规邮箱。合并后核验 GitHub GraphQL `Commit.authors` 的账号映射仅包含已授权作者，不能只检查主要 author；GitHub 自身 committer 与共同作者分开判断。
- 配置只防止新增错误归属，不清除历史。`.mailmap` 不能当作修复 GitHub 账户贡献归属的证据。历史改写涉及 SHA、签名及关联记录，必须另行评估并取得明确授权；不得自行强推主线、解除保护或宣称遗留已清除。当前遗留及事实见[提交身份修复记录](../开发/提交身份修复记录.md)，Issue #85 保持开放。
