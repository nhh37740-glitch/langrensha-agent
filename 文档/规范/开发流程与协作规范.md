# 软件开发流程与协作规范

制定日期：2026-10-23（北京时间）。适用项目：本仓库；本地原目录为 `X:\狼人杀agent`。

本文件规定怎么开展工作，不确定产品需求、技术选型或模块方案。当前阶段统一记录在 [项目说明](../../项目说明.md)，各阶段按用户实际指示推进。

## 1. 基本原则

- 按“规范 → 需求分析 → 架构与设计模式 → 详细设计 → 编码与测试 → 验收交付”的顺序推进。发现前提有误时返回对应阶段修订。
- 用户决定产品目标、范围和优先级。助手可以整理、提问和提出建议，不能将自己的补充写成用户已确认的需求。
- 每轮先识别用户要求的是讨论、记录、制定规范、需求分析、设计还是实施，只完成当前已授权范围。
- 不因用户举例就指定首版内容，不因用户询问某技术就自行采用，不因讨论过功能就开始划分模块或编写代码。
- 用户已明确表达的选择保留原始依据；进入相应阶段时结合完整条件核对，不擅自扩大或抹去已有决定。

## 2. 阶段、产物与推进条件

| 阶段 | 主要工作 | 产物 | 推进条件 |
| --- | --- | --- | --- |
| 开发规范 | 明确流程、职责、记录方法与阶段边界 | 本规范 | 用户明确启动需求分析 |
| 需求分析 | 通过用户陈述和澄清，明确用户场景、功能、约束、范围、优先级与验收口径 | 需求说明及待确认问题 | 用户确认需求基线并同意进入设计；影响设计的关键问题已处理 |
| 架构与设计模式 | 对照需求评估方案，说明技术选型、职责边界、设计模式及取舍 | 架构方案与选型依据 | 用户认可方案并明确详细设计范围 |
| 详细设计 | 在已认可架构下确定模块、数据、接口、权限、交互和测试设计 | 相应设计规格 | 设计与需求一致，实施范围和验收方式明确，并获准开始编码 |
| 编码与测试 | 每项特性或缺陷由 GitHub Issue 进入开发，经分支、PR 和 GitHub Actions 验证后合入主线 | 源码、测试及验证记录 | 约定检查通过，具备可供验收的结果 |

阶段转换依据用户明确指示或已明确覆盖该阶段的授权，不能以沉默、举例、一般性讨论或助手自己的判断代替。复用已有清楚的授权；同阶段内的常规排版和纠错不反复请求确认。

## 3. 各阶段的边界

- 规范阶段：只规定工作方法，不代写需求清单、技术方案或模块设计。
- 需求阶段：回答“谁在什么场景需要什么结果、有什么限制、如何验收”；技术偏好原样登记，不据此展开接口和实现。
- 架构阶段：方案须说明对应哪项需求及取舍依据；未经比较，不以“先进”“成熟”等形容词代替判断。
- 详细设计阶段：明确目标文件或模块、影响范围与验收方式后再准备实施；遵守用户已确定的业务归属约束。
- 实施阶段：不把需求缺口当成自由扩展的授权，遇到影响范围的变更先返回相应阶段处理。
- 验收阶段：区分已修改、已验证、已构建、已部署和线上已验收，只报告有证据的状态。

只读调研可以在当前任务需要时进行；调研结果属于证据或候选方案，不自动成为产品决定。新增依赖、修改业务源码、迁移目录、发布或部署均不能由流程规范本身产生授权。

## 4. 文档与决定记录

- 项目文档统一使用中文文件名和中文正文，名称直接说明用途。`AGENTS.md` 等工具必须识别的固定入口保留原名；第三方参考源码的文件名不在本项目文档整理中改动。
- 严禁在同一目录混放不同层级、不同用途的文件。项目总览放根目录入口；规范、调研、历史草案分目录；后续阶段启动后，其正式文档放对应阶段目录，专题明细和附件放所属主题下。
- 同一层级只放同等职责和粒度的内容，不能将总览、细节、附件、运行产物和临时试稿堆在一起。新建文件前先确定用途、状态及所属目录。
- 临时脚本、试稿、下载文件及中间结果只放项目根目录下的 `临时/对应任务/`，禁止散落根目录、正式文档目录或其他任务目录。无临时任务时不创建空目录；转为正式资料时移至正确位置并更新引用。
- 当前目录约定：`项目说明.md` 为阅读入口；`文档/规范/` 放规范，`文档/调研/` 放调研，`文档/历史草案/` 放未确认的历史资料。阶段未启动，不提前堆建阶段目录。
- 每个主题维护一份正式依据，其余文档链接引用，避免重复维护。
- 明确标注：用户已明确表达、助手建议、待确认、已核验事实和历史记录；不混用这些状态。
- 每项决定保留来源、北京时间日期及适用范围；建议只有经用户采纳才能转为相应决定。
- 修改已确认内容时，记录变化、原因和影响，不静默覆盖原先决定。
- 阶段产物只在对应阶段启动后建立，不提前堆积需求、架构或实现文件。
- 本规范后续按用户反馈修订；规范本身不锁定任何产品玩法、框架或目录结构。

## 6. GitHub 开发与合并流程

用户于 2026-10-23 明确：特性和 Bug 都通过 GitHub Issue 管理并合入主线，使用 GitHub 构建。这里的具体做法是 **Issue 记录工作、PR 合并代码、GitHub Actions 自动构建与检查**。当前仓库已初始化并运行文档检查；应用构建需待业务代码进入后配置。

1. **立项**：每项新特性和每个 Bug 均先建 Issue。特性写清用户要完成的事、范围和验收结果；Bug 写清发生位置、复现步骤、期望与实际结果、证据。标明受影响的业务模块；必要时按本项目规则列出该模块下修改或新增的一级模块及用户可得到的结果。讨论和设计文档仍按阶段流程审定，Issue 不代替需求与设计依据。
2. **开发**：从对应 Issue 建工作分支，在分支内实施并本地验证。不要直接修改或推送主线。一个 PR 聚焦可审阅的改动，并链接对应 Issue；如果同一修复影响多个 Issue，在 PR 中逐一说明。
3. **提审**：PR 目标为主线 `main`，写明改动、验收办法和测试结果。使用 `Closes #编号` 关联可在合并时关闭的 Issue；尚未解决的事项只引用，不误关。前端交互和动画的 PR 附截图或短视频，并说明操作反馈。准备合并时请求 GitHub Copilot 代码审查代理检查 PR；处理其意见，实质改动后再次请求审查。该审查提供建议，最终仍按正式设计和验收结果判断。
4. **GitHub 构建**：GitHub Actions 对每个 PR 和主线变更运行。Python 后端执行依赖安装、静态检查、必要测试与可分发包构建；HTML/CSS/JavaScript 前端执行依赖安装、静态检查、前端构建及关键交互验证。Python 不以“编译成功”代替运行和测试通过；具体命令在代码及构建方案确定后落地。
5. **合并与标记**：保护 `main`，要求经 PR 合并且必需的 Actions 检查通过；GitHub Copilot 代码审查已完成且意见已处理，再审阅确认符合 Issue 验收内容后合并。若代理审查暂不可用，保持 PR 待合并并说明原因。每个新功能合入后，在该功能对应的主线提交上创建唯一 Git tag，能追溯到 Issue、PR 和构建结果；Bug 仍走 Issue/PR 流程，不因此自动视作新功能。合并后核对 Issue 关闭状态和主线构建结果。构建通过只代表构建与检查完成；最终还须部署到用户服务器，核对部署版本、实际入口和线上对局结果，分别记录部署及线上验收证据。

仓库已配置中文 Issue/PR 模板、基础 Actions 与主线保护规则；待业务代码出现后补全 Python 与前端构建命令，并用一次特性和一次 Bug 的真实改动验证全流程。业务代码在 Codex Cloud 开发，本地不编写业务代码。

用户于 2026-10-23 补充：GitHub Agent 必要时可在本仓库 Discussions 留言，帮助人类追踪工作与阅读审查结果。留言应链接对应 Issue 或 PR，说明进展、发现或待处理问题；讨论内容不代替正式设计决定。开发日志写在对应 Issue、PR 或 Discussion 中，每条正文不超过 200 个汉字，优先写明变化、验证结果及未决事项。

依据：[GitHub 关联 PR 与 Issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)、[保护主线](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[Python 构建与测试](https://docs.github.com/en/actions/tutorials/build-and-test-code/python)、[Node.js 构建与测试](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)。

## 7. 最小功能内核与版本图

用户于 2026-10-23 明确：**从最小功能内核做起，每个新功能打一个 Git tag，每个版本用 [Archify Skill](https://github.com/tt-a1i/archify/tree/main/archify) 画图**。实施顺序从可运行、可测试的最小对局闭环开始，再按 Issue 逐步加入角色能力、AI 决策、检索辅助和网页表现；这只是开发顺序，不降低首个可玩版本已确认的完整对局验收范围。

每个版本的功能 PR 应用 Archify 根据该版本的实际设计与实现更新适合的架构图、流程图或状态图，并在 PR 中核查图与代码一致。正式图及可编辑图源按版本归入同一专题目录，临时生成物仍遵守第 4 节的目录规则。图随 PR 合入主线后，再为新功能的主线提交打 tag；图中应能识别对应版本及来源，不把计划中未实现的功能画成已交付。版本图可用于审阅与交流，不能代替源码、测试或线上验收证据。

本机已于 2026-10-23 安装 Archify Skill 3.2.0；云端使用仓库内同版 Skill。安装不表示 tag 或版本图已生成。
