## 2. 用一次投票串起代码

假设：4 号已绑定到会话，当前能投票，7 号是合法目标。以下编号是**讲解用合成数据**，不是可直接提交到任意一局的命令：

```json
{
  "request_id": "vote-001",
  "phase_id": "当前窗口的真实编号",
  "expected_version": 42,
  "tool": "exile_vote",
  "payload": {"target": 7}
}
```

请求没有 `actor` 字段。`web.session` 根据 cookie 摘要查询会话，再调用 `bind_player`；`PlayerSession.submit` 将服务器绑定的席位传给 `_submit`。`PlayerSession` 是“只能按这个席位请求服务”的门面，`GameService` 是能持有完整快照和数据库的受信应用服务，两个类碰巧在同一个文件中。

`_submit` 开始事务、加载 JSON 快照，再调用 `reduce_action`。规则先检查请求格式和旧回执，再检查窗口、版本、工具、参数、目标。通过后复制状态，调用 `_apply`，增加版本，把回执放入 `receipts`。服务层调用 `save`，事务提交。**第一次成功行动**使 42 变为 43；完全相同的请求重试则返回原回执，不再次投票。

如果抛出 `Rejected`，服务层只保存拒绝审计，提交审计后再抛出异常；快照和版本不变，Web 返回 409。其他未捕获异常由事务上下文回滚。成功的 HTTP 响应则重新 `view()` → `present(view)`；它返回供页面显示的数据，不直接返回内部回执。重新读取与行动提交是两个事务，因此可能看到更新后的局势。

这三个编号各管一件事：`request_id` 防重试重复生效；`phase_id` 防行动落到另一窗口；`expected_version` 防基于旧局势提交新选择。回执检查排在后两者前面，所以已成功请求在局势变化后仍可重放结果。完整顺序见[时序图](一次行动.html)。

## 3. 想研究游戏规则，再往里走一层

把 `state` 理解为“一局的完整账本”：玩家、阶段、队列、事件和请求回执都在里面。它不是数据库连接，也不是模型聊天历史。

- [tools / targets](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/full_game.py#L273-L327)：按角色、当前阶段和存活情况，列出能做什么、能选谁。
- [_apply](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/full_game.py#L330-L409)：执行已经校验的技能；满足本窗口完成条件后调用 `_settle`、`_advance`。
- [_settle / _advance](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/full_game.py#L161-L270)：汇总投票、插入平票等后续任务、寻找下一个行动窗口。
- [_kill / _victory](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/full_game.py#L99-L154)：处理死亡触发及胜负。

这是有限状态机配合任务队列。规则函数没有数据库或模型 I/O；不过会生成 UUID，建局会随机发牌，不能把“纯规则”理解成所有输出字段都能逐字确定重放。

## 4. AI、检索、札记分别做什么

**AI 玩家选行动。** [web.advance](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/web.py#L234-L259) 在存在待行者、真人不在待行名单且未结束时，绑定下一位 AI 的会话。`DecisionRunner` 取得该玩家视图和合法工具，调用模型；模型提出 `tool_calls`，由 `dispatch` 执行。行动走 `session.submit`，查询走 `session.query`。`wolf_chat` 可以继续思考，完成一次最终行动则结束窗口；默认最多 3 轮模型调用、每次回复最多 8 个工具。模型故障或轮数耗尽走受控弃权，窗口已关闭则停止。[循环与回退](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/ai.py#L347-L421)

**检索找已有资料。** `PlayerSession.query` 每次重新取自己的 `view()`；历史文档由可见事件生成，世界书条目由 `visible_entries(book, role)` 过滤。之后才切块和评分。`semantic.py` 用本地 ONNX 模型计算向量，失败时 `_rank` 明示退回词项检索；不是每种查询都需要向量，例如人物总结直接取可见发言。候选索引每次重建，向量缓存可以复用，但缓存不充当跨玩家搜索候选库。[检索分支](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/retrieval.py#L163-L221) / [缓存与评分](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/semantic.py#L185-L237)

**真人札记整理回答。** `/api/query` 先检索，再由 `assistant.assist` 可选调用同一个模型连接；只给 `compose_note` 工具和已过滤的来源，结果返回真人编辑，不自动发表。来源编号会检查是否属于本次提供的集合；这能防引用不存在的编号，不能证明模型每句推论都正确。[札记实现](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/assistant.py#L11-L90)

## 5. 权限边界要连同调试例外一起读

普通链路有两道检查：一是 `player_view` 决定能看到哪些事件、身份和技能；二是 `reduce_action` 再次检查能做什么。`presentation.present` 只把视图转换成世界内称谓和展示字段，不能代替授权。世界书改变内容与称谓，完整局仍运行同一套 `mist-v1` 裁定。

**当前 Web 调试默认开启。** [GET /api/debug](https://github.com/nhh37740-glitch/langrensha-agent/blob/182133f294a5eed10460b097f9f5e6e5a8ffb9e9/src/langrensha/web.py#L180-L214) 在会话调试开关打开时直接读取 `host_snapshot` 和 `host_decisions`，经 `debug_timeline` 返回秘密身份、模型显式说明、工具记录和狼队对话。关闭后该接口不返回这些调试数据；这是现有开发观察功能，不是普通玩家授权链路。不能据普通 `player_view` 就宣称“所有 HTTP 返回都不含秘密”。

模型服务收到的是序列化上下文和工具定义；Python 编排器持有 `PlayerSession`。后者内部仍引用 `_service`，下划线只是约定，不是沙箱。现有 Import Linter 限制静态依赖，运行时安全仍依赖固定身份、工具白名单及规则校验。不要把“模型不能凭工具直接写库”扩大成“任意恶意 Python 插件都无法访问数据库”。
