## 1. 度量方法

- 工具调用：统计同一 Agent 会话中 `tool_use` 条数，按任务时间窗汇总；同一文件被多次读取单独列出。
- 构建测试耗时：取 GitHub Actions 各检查的完成时长，使用同一仓库与同一 runner 规格；本地未构建环境，不把推测计入。
- 失败证据：记录首次失败的检查、错误摘要、修复次数与重跑次数。

## 3. 结果与限制

- 两次任务规模不同（#101 改 11 个文件，#96 改 2 个文件），工具调用数不能直接归因于精简模式。本记录只作为基线，不宣称因果。
- 前端检查约 11 分钟，主要耗时在 Playwright 全量用例；两次都只跑一轮，耗时差异属于 runner 波动，精简模式没有也不应削减这一步。
- Python、版本图与文档检查均在 1—2 分钟内；修改后 Python 检查略快，同样不能归因。
- 两次各有一个文件被读两次，均有明确原因：#101 核对工具描述上下文；#96 分两段读取外部技能全文。未出现无理由重复通读或哈希校验。
- #101 的 Python 检查首次失败后保留完整日志，只改一处契约测试并重跑一次；#96 首次即通过。失败证据均保留在 PR 检查记录中。

## 4. 后续对比协议

要在同一规模任务上得到可归因的对比，下一次演练应：

1. 选两个同类型、同文件数的小任务（各改 1—2 个文档或单测文件），一个在规则约束下执行，一个按原流程执行。
2. 固定度量窗口为 Issue 创建到 PR 合并。
3. 记录工具调用、重复读取、首次失败与重跑次数、五项检查耗时。
4. 只比较同类任务；跨类型数据仅作基线，不用于证明精简模式有效。
